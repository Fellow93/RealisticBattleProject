# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Realistic Battle Mod (RBM) for Mount & Blade II: Bannerlord. A comprehensive combat overhaul mod that rewrites damage calculations, armor mechanics, AI behavior, and adds a stamina/posture system. Built on Harmony 2.4.2 for non-invasive runtime patching of game methods.

Current version: v4.6.1 (`RBMXML/SubModule.xml`). Targets Bannerlord v1.5.4+ (per the
`DependedModules` entries there); currently developed against v1.5.4.

## Build

**Solution:** `RealisticBattle.sln` — .NET Framework 4.7.2, x64 target.

Build with Visual Studio (2017+) or MSBuild:
```
msbuild RealisticBattle.sln /p:Configuration=Release /p:Platform="Any CPU"
```

All 8 projects output DLLs to `../../RBM/bin/Win64_Shipping_Client/` (relative to each project folder, resolving to the `RBM/bin/` directory within the Bannerlord Modules tree).

Single-project build (from memory — MSBuild path is under VS `18\Community`, and `Platform` must be quoted with its space):
```
"C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe" RealisticBattle.sln /p:Configuration=Debug "/p:Platform=Any CPU" /t:RBM /verbosity:minimal
```

**Debug launch:** Bannerlord.exe with `/singleplayer _MODULES_*Native*SandBoxCore*SandBox*StoryMode*CustomBattle*RBM*_MODULES_`

No test suite exists — testing is manual via in-game verification.

## Architecture

### Module Structure (8 C# projects)

**RBM** — Main coordinator. Entry point: `RBM.SubModule` (extends `MBSubModuleBase`). Manages Harmony instance lifecycle, conditionally patches/unpatches each subsystem based on config toggles. References RBMAI, RBMCombat, RBMStance, RBMTournament, RBMCampaign and RBMAutoResolve.

**RBMAI** — Battle AI (the posture/stamina system, AI kick/bash and the combat slow motion moved out to RBMStance on 2026-10-13). Patcher entry: `RBMAiPatcher` (uses `Harmony.PatchAll()`, so file location is cosmetic — patches are discovered by attribute, not registered by hand). References RBMConfig and RBMStance (Frontline reads posture/stamina, the developer battle-stats overlay `AiModule/Diagnostics/BattleStatsLogic.cs` shows the kick/bash counters). As of 2026-07-18 the module was reorganized from a handful of multi-thousand-line monoliths into subsystem folders under `AiModule/`. Large classes were split across files using `partial class` (and, for `Utilities`, partial static files at project root) so no call sites changed. Namespace stays flat `RBMAI`; the old-style csproj lists every file with an explicit `<Compile Include>` — **update it when adding/moving files**. Layout:
- `AiModule/Behaviors/` — formation behavior patches (`SkirmishBehaviors`, `DefenseBehaviors`, `FlankBehaviors`, `AdvanceBehavior`, `AgentSpeedAndParams`, `MiscBehaviorPatches`); custom `RBMBehavior*` subclasses under `Behaviors/Custom/`.
- `AiModule/Tactics/` — `partial class Tactics` split into `TacticsState`, `DamageTracking`, `Lifecycle`, `TacticOverrides`, `FormationCounts`; custom `RBMTactic*` subclasses under `Tactics/Custom/`. ⚠️ `Tactics.EarlyStartPatch` is referenced by fully-qualified name in `RBMAIPatcher.FirstPatch`, so it must stay nested in `partial class Tactics`.
- `AiModule/Misc/MissionStartReset.cs` — the one place that clears every RBMAI static holding an `Agent`/`Formation` (plus native `Formation._simulationFormationTemp`), called from `RBM.SubModule.OnBeforeMissionBehaviorInitialize` (top of `Mission.AfterStart`, main thread, before any AI tick). **Add any new Agent/Formation-keyed static there.** Not a Harmony patch on purpose: RBMAI's `PatchAll` only runs from `RBMAIPatchLogic.EarlyStart`, inside `AfterStart`, and `FirstPatch` unpatches on every game start/load. (RBMStance's statics have their own `StanceReset`, called from the same hook.)
- `AiModule/Agents/` — `partial class AgentAi` patches (`AgentStats`, `CombatFixes`, `Weather`, `TickPatches`). `AgentStats`' `SetAiRelatedProperties` postfix (Priority.Low) sets the AI block/parry/aim values; picks the posture-tuned block/parry set under `rbmStanceEnabled && postureEnabled`. Stamina's multipliers on top are RBMStance's `StanceStatsPatch`.
- `AiModule/Voices/FormationShoutsLogic.cs` — formation shouts (MissionLogic, added in `RBM/SubModule.cs` under `rbmAiEnabled` when `formationShoutsEnabled` or `orderReactionDelayEnabled` is on; each feature re-checks its own toggle). Soldiers echo/answer player orders (`Team.OnOrderIssued`), AI captains call movement-group/arrangement changes, plus halt/formed grunts, charge yells, a contact roar (`OnMeleeHit`), melee chatter and per-culture infantry march cadences (`Cadences`, keyed by culture StringId), horns (module sounds `rbm/horn/charge|order/<culture>`: mounted formations' charge horn leads the yells, Aserai/Nord order horn; own longer carry distances `Horn*`), all through one voice queue with per-agent cooldown and a global per-second cap. `orderReactionDelayEnabled` (experimental) re-sets each man's engine decide time from the `OnOrderIssued` handler, which fires right after vanilla's `AfterSetOrder` default. That only delays Charge → Move; Move → Move is delayed by `AiModule/Orders/OrderReactionHold.cs` (a Priority.Last postfix on `HumanAIComponent.GetFormationFrame`, worker + serial threads, managed reads only) which returns each man's OLD frame until his release time, stamped by a prefix on `OrderController.AfterSetOrder`; charges are never held. AI orders are stamped by prefixes on `Formation.SetMovementOrder`/`SetArrangementOrder` (AI-controlled formations, real group/arrangement change only; these run on the async AI thread, so a thread-static `System.Random`, never MBRandom). Its Agent-keyed static is cleared in `MissionStartReset`. ⚠️ Main thread only: AI order changes are POLLED in `OnMissionTick`, never via `Formation.OnBeforeMovementOrderApplied`/`OnAfterArrangementOrderApplied` (those fire on the async AI thread); all state is instance fields cleared at mission end.
- `AiModule/Frontline/` — the Frontline system (everything from the old `Frontline.cs`): `FrontlineDecision.cs` (the `partial class Frontline` decision AI), `FrontlinePositioning.cs` (`Frontline.OverrideFormation`; reads posture/stamina from RBMStance's `AgentStances` on the worker thread, gated `rbmStanceEnabled && postureEnabled`), `FormationMovement.cs` (HumanAIComponent movement gates), `AgentPanicFix.cs`. ⚠️ Load-bearing worker-thread crash-safety code — move verbatim, never restructure the gates.
- `AiModule/Formations/` — general formation-grid safety patches: `FormationGridGuards.cs` (`OverrideLineFormation`, from the old `Behaviours.cs`). ⚠️ Also load-bearing worker-thread crash-safety — move verbatim.
- `AiModule/Orders/` — movement-order patches. `AiModule/UI/` — formation-marker patches. `AiModule/Siege/` (+ `SiegeArcherPoints/`), `AiModule/Spawning/`, `AiModule/Misc/`. `AiModule/Diagnostics/` — AI behavior log + the developer battle-stats overlay.
- `Utilities/` (project root) — `public static partial class Utilities` split into `Utilities.Formations.cs` / `.Targeting.cs` / `.Geometry.cs` / `.Combat.cs`.

**RBMStance** — the posture/stamina system, AI kick / shield bash / weapon bash and the combat slow motion, split out of RBMAI on 2026-10-13 so they work with RBM AI off. Gated ONLY on its own module switch `rbmStanceEnabled` (default on, XML `/Config/RBMStance/Enabled`), never on `rbmAiEnabled`: own Harmony instance `com.rbmstance`, patched by `RBMStancePatcher.DoPatching` (`PatchAll`) from `SubModule.ApplyHarmonyPatches` at game start, right after RBMCombat (off = no patch installed, no Stance behavior added). Sub-options read at run time: `postureEnabled`, `staminaEnabled`, `postureGUIEnabled`, `playerPostureMultiplier`, `aiKickBashEnabled`, `hitStopEnabled` (their XML keys stay under `/Config/RBMAI`, no migration); settings screen section "RBM Stance". References RBMConfig only; namespace flat `RBMStance`; explicit `<Compile Include>` csproj — **update it on add/move**. RBMAI, RBMCombat and RBM reference it. Layout:
- `Stance/` — `StanceLogic` (MissionBehavior) split into `StanceLogic.Core.cs` / `.Visuals.cs` / `StanceLifecyclePatches.cs` / `StanceMiscPatches.cs`; its huge `CreateMeleeBlowPatch` split via nested `partial class` into `MeleeBlowPatch.cs` (orchestration + attributes) / `.Math.cs` (calculators) / `.Ranged.cs`. State types in `Stance.cs` + `PostureDamageTable.cs`; `AgentStances.values` is a `ConcurrentDictionary` because RBMAI's Frontline job and the parallel stat update read it off the main thread — keep it concurrent. `PlayerExhaustion.cs` (first-person tiredness). `StanceStatsPatch.cs` — stamina's multipliers on the driven properties, a `SetAiRelatedProperties` postfix at `Priority.Last` + `[HarmonyAfter("com.rbmai","com.rbmcombat")]` (after RBMCombat's reload and RBMAI's AI values). `HitStopLogic.cs` — the combat slow motion (MissionLogic, added in `RBM/SubModule.cs` under `rbmStanceEnabled && hitStopEnabled`, independent of RBM AI): a kill/knockout by the player (`OnAgentRemoved`) needs nothing else; the posture-break stop is raised by `MeleeBlowPatch` through the static, `Instance`-null-safe `HitStopLogic.TriggerPostureBreakHitStop()` (so only with `postureEnabled`; parries raise no stop). RBMStance never references RBMAI. `StanceReset.cs` — the per-mission reset of every RBMStance static holding an Agent or behavior (the stance store and drop/formation queues through `StanceLogic.ClearMissionState`, which the LoadMission/OnDeactivate/tournament EndMatch patches share), called unconditionally from `RBM.SubModule.OnBeforeMissionBehaviorInitialize` next to `MissionStartReset` (not a Harmony patch, so it also runs with the module off). **Add any new Agent-keyed static there.** The patches sharing a target with RBMCombat (`CreateMeleeBlow`, `MeleeHitCallback`, `OnAgentShootMissile`, `EquipItemsFromSpawnEquipment`, `OnWieldedItemIndexChange`) carry `[HarmonyAfter("com.rbmcombat")]`, the order they always had in RBMAI.
- Posture rules (2026-10-14), all tuning in `Stance/PostureTuning.cs`: a break (melee, ranged, chamber) calls `Stance.BreakPosture`, which resets posture at once to the branch's share (0.75, attacker's own landed hit 0.33; the direct-hit defender branch resets too) and bumps `postureBreakCount`; the break effects fire once, on the blow that empties posture. The kick/bash knockdown (`AiKickBashKnockDownPatch`, a Priority.Last postfix after the posture patch) compares the victim's `postureBreakCount` against its prefix's `__state` to knock down on the blow that broke him, since posture is already refilled by then. Normal regen pauses 1.2 s after combat posture loss; quick regen also needs 10 s without any posture exchange. Perfect parry (defender): the matching block row's cost × 0.25 (weapon) / × 0.5 (shield), then a refund of 5% / 2.5% of max posture if it left him unbroken; a parry break still staggers and (weapon parry) crushes through at × `PerfectParryCrushThroughFactor` 0.5 (without the small-overflow scaling a block break gets), but never disarms or dismounts. The zero-damage posture blows (`BuildPostureBlow`) carry `BlowFlags.NoSound` on purpose, so a break never adds a body-hit sound to the clash or to the real hit. Chamber = defender's weapon-parry cost ×0.5 (plus the weapon refund) / attacker's parry result ×1.5; a landed hit costs the attacker ×0.2 and the defender its `InflictedDamage`; a missile likewise costs its `InflictedDamage` (only Arrow/Bolt/Javelin/ThrowingAxe/ThrowingKnife; body hits in `StanceLogic.OnAgentHit`; a raised-shield block, which registers no blow, in `StanceLogic.OnMissileHit` as min(shield damage, `ShieldMissilePostureCap` 2 for arrows/bolts/sling stones, `ShieldThrownPostureCap` 6 for thrown) × Arrow Catcher; a shield on the back costs nothing; the same missile's body hit within 0.5 s of its shield charge is skipped). The speed term counts closing speed only (4 posture per m/s, horizontal). All of it lives in plain `Stance` fields written on the main thread.
- `UI/` — `StanceVisualLogic` / `StanceVisualVM` (prefab `CombatUI.xml`), added under `postureEnabled && postureGUIEnabled`. Its sub-option `postureVerticalBarsEnabled` (default off, XML `/Config/RBMAI/PostureVerticalBarsEnabled`) swaps the player's small horizontal bars for two large right-edge vertical bars (`ShowPlayer*BarVertical`, `FillBarVerticalWidget` bound to the same `PlayerPosture`/`PlayerStamina` ints).
- `Utilities/StanceUtilities.cs` — `GetEffectiveArmorWeight`, `GetComHitModifier`, `HitWithWeaponBlade` (moved from RBMAI's `Utilities.Combat.cs`).
- `KickBash/AiKickBash.cs` — host class `KickBash` (`KickBash.AiKickBash`, `KickBash.AiKickBashComponent`, the knockdown and spawn patches). AI kick / shield bash / weapon bash, gated by `rbmStanceEnabled && aiKickBashEnabled` (off = vanilla), independent of RBM AI; works with the posture system off too (damage and knockdown only, its posture/stamina effects check `postureEnabled`). The component is attached to every human by the `Agent.WieldInitialWeapons` postfix. The native AI never kicks (`AiKick` is dead in game), so an `AgentComponent` on every human injects the contextual `Kick` input through `OnAIInputSet` (a bash holds `DefendUp` first) and suppresses the AI's own input until the action plays out. ⚠️ `OnAIInputSet` runs on the engine's AI thread: it only reads volatile fields that `OnTick` sets, never queries the engine. The file's header comment is the rules reference (openings, relative-skill attempt and knockdown rolls, costs, stagger and posture-break knockdowns); all tuning constants sit at the top of `AiKickBash`. It spans three modules: the blended Athletics/weapon skill and the kick/bash magnitudes are in `RBMConfig/Shared/SkillDamage.cs`, the damage itself (punch model, none into a raised shield) is the `isKickOrBash` branch of `DamageRework.Core.cs`, and the hit shapes are in `RBMXML/RBM_spear_combat_parameters.xml`: `kick_shieldbash_radius` (kicks), `shield_bash_radius` (shield bashes, around the forearm) and the `custom_collision_capsule` `r` of the three `weapon_bash_params_*` (the capsule, not `collision_radius`, is a weapon bash's hit shape). Keep the three reaches about equal: the AI starts all of them from one `TriggerDistance`. The victim's posture/stamina loss is the posture patch's normal direct-hit rule (by damage), so retuning kick damage also retunes posture loss and the posture-break knockdown.

**RBMCampaign** — Campaign-layer overhaul: the "spoils" troop economy, the settlement wealth ledger, the village-to-town production chain, and equipment-based strategic troop power (the auto-resolve itself is RBMAutoResolve, above). Patcher entry: `RBMCampaignPatcher.DoPatching` (calls `PatchAll` + registers the party-screen widget). References RBMConfig and RBMAutoResolve. Unlike the combat modules, most logic lives in `CampaignBehavior` subclasses, not just Harmony patches — they are added in `OnGameStart` for `Campaign` sessions (`RBM/SubModule.cs`), starting with Spoils, TroopUpkeep, `RBMCampaignSessionBehavior` (session cache resets + the hourly/before-save `BufferedLogWriter.FlushAll`; it holds the slot the auto-resolve behavior used to, and later behaviors rely on that order), Spectate, Economy, SettlementWealth. Organized into folders (namespace stays flat `RBMCampaign`; the old-style csproj lists every file with an explicit `<Compile Include>` — **update it when adding/moving files**). See `RBMCampaign/ARCHITECTURE.md` for the full file map.
- `Spoils/` — `SpoilsPool` (a `partial static class` split across several files) is a per-troop-**stack** purse in gold (1 spoils point = 1 gold), keyed by `party.Id + "#" + character.StringId`, persisted via `SyncData` key `RBM_troopSpoilsGold`. Fills from battle loot, raid/siege plunder, and the stack's **whole** daily wage; drains on upgrades, field maintenance, food, carousing, paid healing and luxuries. Surplus over the cap is **drunk in settlements** (crediting that settlement's purse), NOT returned to the owner's gold — the one spoils→gold exit is the leader's cut in `SpoilsPool.LeaderCut.cs`, which draws from the purse first and so mints nothing.
- `Upkeep/` — `TroopUpkeep` (+ `.Food`/`.Healing`/`.Luxury`) and `TroopMarketFeedback`, which lands troop spending in a settlement's purse.
- `Upgrades/` — gold-cost/tooltip patches, the reimplemented AI (`UpgradeReadyTroops`) and player-side upgrade paths, and `UpgradeSupply` (supply-town gate + market draw + payment leg).
- `Wages/TierBasedWageModel.cs` — the per-tier wage table (foot 20/30/40/60/120/240, horse 30/40/60/120/240/480). **Not configurable** — it applies whenever the module's patches are on.
- `Settlements/` — the two-pot wealth ledger (`SettlementWealth` + `SettlementGoldFunnel` over vanilla's writes), tariffs, ransoms, garrison/militia/admin/construction upkeep, workshop purses.
- `Production/` — village production, villager convoys/deliveries, town food supply and storage, citizen and workshop demand.
- `Economy/` — market prices and liquidity, caravan capital, recruit supply, trade-good values.
- `Power/` — `StrategicTroopPower` (equipment-based party strength, priced through RBMAutoResolve's kit model; its `Enabled` also needs `rbmCombatEnabled` — with RBM Combat off the game's own strength is used, there is no combat-off pricing path, and `ArmyStrengthFloorPatch`'s 700 falls back to vanilla's 1000) and the strategic-AI gates (`SiegeDecisionGate` etc.). `Spectate/` — no-agent AI-vs-AI spectator battle.
- `MercenaryCompanies/` — neutral hire-only mercenary companies (`mercenaryCompaniesEnabled`): two per main culture, each its own runtime minor clan (StringId prefix `rbm_merc_co_`, created on the first campaign hour so old saves get them) with one leader and one party. They never join a kingdom on their own (vanilla barters, decision proposals, minor-faction spawning and the hire dialog are blocked for them); an army leader hires one for gold (AI on `ArmyCreated`, the player from the army management screen, with injected price/cart-gold widgets), and an hourly `MercenaryContracts.Reconcile` takes the company back out of the kingdom once its party no longer serves in that kingdom's army (never mid-battle/siege, nor while its party is lost and its leader is the employer's enemy's captive). Excluded from `MercenaryContractPay`. ⚠️ Every patch must stay a no-op for clans that are not companies (`MercenaryCompanies.IsCompany`).
- `UI/` — `RBMTroopSpoilsBarWidget` (a `FillBarVerticalWidget`) and the inventory weight column, both injected into native prefabs. `SpoilsBarPrefabPatch` also injects `RBMTroopHoverTooltipWidget` (party-screen troop-row hover → troop tooltip, gated on `rbmCampaignEnabled` + `troopPerksEnabled`) into `PartyTroopTuple.xml` and `PartyTroopTupleLeft.xml`; the PartyScreen codegen skip runs when either the spoils bar or the hover is on.
- `Diagnostics/` — `SpoilsLog` (`logs/campaign/`), `EconomyLog` (`logs/economy/`), `MercenaryLog` (`logs/mercenaries/`, the mercenary companies' lifecycle; log them here, never through SpoilsLog), `StuckPartyLog` (`logs/stuckparties/`, fed by the observer `StuckPartyLogBehavior`: hourly pass over `MobileParty.All`, one STUCK line per party with a move target that stays within 1 map unit for 24 h, incl. the engine's private `_aiPathNotFound`); each gated by its own config toggle (the auto-resolve's `SimulationLog` is in RBMAutoResolve). `TestBattleCommand` is the debug console command `campaign.rbm_test_battle [countPerTroop=5] [attacker=<groups>] [defender=<groups>] [player=attacker|defender]` (all-troop-types field battle, per-side culture/mercenary/minor-faction filters; the player's party is snapshotted and restored when the encounter is over, polled from `RBM.SubModule.OnApplicationTick`). With no parameters it opens a vanilla-inquiry setup (`TestBattleCommand.Setup.cs`: Default → count, Custom → attacker groups → defender groups → side → count → start or save as preset, Last used / Load preset → count, Delete presets; presets in `TestBattleCommand.Presets.cs` are one XML per preset in `Configs/RBM/TestBattlePresets/` plus `last_used_test_battle.xml`, written on every start, like the custom battle presets); each step opens on the next tick, never inside the previous popup's callback (the popup closes itself after the callback). Every campaign log writes through `BufferedLogWriter` (one open buffered handle per file, flushed hourly/before save by `RBMCampaignSessionBehavior`, closed on game end by `RBM.SubModule`) and prunes with `LogRetention` — both in `RBMConfig/Shared/Logging/` (namespace `RBMConfig.Logging`), shared with RBMAutoResolve, whose `SimulationLog` flushes its own writer so it works with RBM Campaign off. Never add a per-line `File.AppendAllText` or a `Debug.Print` copy of log lines.

### Harmony Patching Pattern

All game modifications use Harmony `[HarmonyPatch]` attributes on static inner classes with `Prefix`, `Postfix`, or `Finalizer` methods. Patches target `TaleWorlds.MountAndBlade` types via reflection. Each module has a dedicated `Harmony` instance (`com.rbmai`, `com.rbmcombat`, `com.rbmstance`, `com.rbmt`, `com.rbmmain`, `com.rbmcampaign`, `com.rbmautoresolve`) enabling selective enable/disable.

The patching lifecycle flows: `SubModule.OnSubModuleLoad()` → loads config → `RegisterSubModuleTypes()` / `OnGameStart()` → `ApplyHarmonyPatches()` which conditionally patches each module.

### Configuration

**Changing a saved setting for every player in a release:** add one entry to `ForcedSettings` in `RBMConfig/Config/RBMConfig.Core.cs` (new unique id, XPath, value) and give the code default the same value. It is written once onto each saved config on the first start of that release (ids recorded under `/Config/AppliedForcedSettings`; fresh configs only mark them), and the player's later choice sticks. Never edit or remove a shipped entry. Only for absolute values: a change relative to the player's own value (like the sling stone rescale) still needs a hand-written marker migration. Never bump `CONFIG_VERSION` for this, it resets the whole config.

Settings are static fields on `RBMConfig.RBMConfig`, persisted to user XML at `Utilities.GetConfigFilePath()`. Key toggles: `rbmAiEnabled`, `rbmCombatEnabled`, `rbmStanceEnabled` (RBMStance's module switch, independent of `rbmAiEnabled`; `postureEnabled`, `staminaEnabled`, `postureGUIEnabled`, `playerPostureMultiplier`, `aiKickBashEnabled` and `hitStopEnabled` are its sub-options), `rbmTournamentEnabled`, `rbmCampaignEnabled`, `simulationEquipmentEnabled` (RBMAutoResolve's module switch, independent of `rbmCampaignEnabled`). Each toggle gates whether the corresponding Harmony patches are applied. RBMCampaign also reads tuning multipliers (e.g. `troopUpgradeCostMultiplier`, where `0` disables the spoils system entirely) — see `RBMConfigViewModel` for the full set.

### XML Data Files

`RBMXML/` contains 30+ XML files loaded by Bannerlord's XML system (registered in `SubModule.xml`). These modify items (weapons, armor, horses), crafting pieces, siege engines, NPC characters, and weapon descriptions. `XmlLoadingPatches.cs` handles XML merging/preprocessing.

`RBM_WS_XML/` contains compatibility files for the War Sails (Naval) DLC.

Troop skills/levels/equipment rosters in `RBMCombat_unit_overhaul.xml` (+ the WS one) can be edited with the local page in `tools/TroopLoadoutEditor/` (run its `Build-TroopLoadoutData.ps1` first; its README explains how `XmlLoadingPatches` applies those files). Upgrade targets are edited with `tools/TroopUpgradeTreeEditor/` (tree diagrams + checks), which has no data or build script of its own: it loads the loadout editor's data and `troop-loadout-core.js`, so both pages export the same files through one splice path (re-run the script after exporting from either). Its README lists the verified game rules (later definition replaces `UpgradeTargets`, cycles crash, no count limit, tier ≤ → 0 XP). Items in RBM's item files are edited with `tools/ItemEditor/` (run its `Build-ItemData.ps1` first; it also loads `troop-loadout-core.js`): the export patches only changed attributes in every RBM file defining the id (both ranged twins), and its README covers RBM's full-replacement item rule and the tier/price formulas. Crafting pieces and templates are edited with `tools/CraftingEditor/` (run its `Build-CraftingData.ps1` first): RBM's crafting files are appended, not merged, so an id is deserialized again after vanilla's (start-tag attributes reset, child elements only when present, usable pieces accumulate); the page replays that and recomputes every crafted item's stats with the game's crafting math plus RBM's patches (README: formulas and approximations).

### Large Utility Files

RBMAI, RBMCombat and RBMConfig each have their own `Utilities` (partial static files in RBMAI/RBMCombat, see above) with helpers for combat math, physics and config management; RBMStance has `StanceUtilities`.

**Shared damage math lives in `RBMConfig/Shared/`** (2026-09-26), because RBMStance (the posture system, formerly in RBMAI) does not reference RBMCombat (RBMCombat references it) and RBMConfig is the one module both reference:
- `SkillDamage.cs`: `GetSkillBasedDamage` (the per-weapon-class skill coefficient/clamp table) and the punch magnitude helpers (`GetPunchMaterialFactor`/`GetPunchMagnitude`). `MeleeSkillDR`/`MeleeSkillMod` (2026-10-14) are the melee-only skill curve (c = 200, scaled to equal the shared 600 curve and clamp(skill/250) at skill 100), used by melee swing/thrust speed, thrust energy, `GetSkillBasedDamage` for melee blows, the melee attack/handling animation speeds (`CalculateVisualSpeeds`, live in `RangedRework.OverrideWeaponEquipped` + tooltip), the weapon tooltips' damage and the auto-resolve (+ CraftingEditor mirror); missiles and kicks/bashes keep `MissileBallistics.EffectiveSkillWithDR`.
- `BlowDamage.cs`: `RBMComputeDamage` (armor, penetration and blunt trauma). Trauma (2026-10-14): every damage type's trauma (the stopped part × carry × armour reduction) is × `GetTraumaMaterialFactor` (mail 1.2, plate 0.8, else 1; from the `armorMaterial` argument, so callers that pass `None` — tooltips, shield damage — get 1). Blunt carry = `BluntTraumaBase` 0.6 × per-class `ExtraBluntFactorBlunt`, × `UnarmedBluntTraumaFactor` 0.75 for `"unarmedAttack"` (kicks/bashes/punches; charges and falls are `"otherDamage"`); cut/pierce carries are the per-class `ExtraBluntFactorCut/Pierce`. The penetration threshold has no material factor on purpose (armor values are set by a bodkin; cuts never get through mail/plate). The per-class rules are two lookups, not a switch: `GetThrustBonus(weaponType)` (×One/TwoHandedThrustDamageBonus on Pierce for the thrust-scaled classes, 1 otherwise; the auto-resolve divides by it because its thrust magnitudes are already unscaled) and the factor row (only the listed classes read the config; any other string, e.g. `"unarmedAttack"`, gets the base rule). Weapon-class aliases (LowGripPolearm → OneHandedPolearm, Pick → Mace) live in `WeaponTypeKeys.NormalizeWeaponType`, used by both `BlowDamage` and `SkillDamage`. The shared math has no UI side effects: the armor penetration message is shown by its caller in `DamageRework.Core.cs`. Per-class blunt factors are relative to the base, so changing the base needs a saved-config rescale for any class meant to keep its trauma (sling stones: `SlingStoneBluntBaseRescaled` in `RBMConfig.Core.cs`).
- `ThrustEnergy.cs` (2026-10-12): melee thrust speed (`CalculateThrustSpeed`) and thrust energy (`OneHanded`/`TwoHanded`, raw, before `ThrustMagnitudeModifier`), used by the live blow + tooltip (RBMCombat `Utilities.Physics.cs` forwarders) and the auto-resolve (`SimulationWeaponModel.GetThrustEnergy`). The body term runs at no more than the class's median thrust speed (`GetReferenceThrustSpeed`, so a light shaft no longer carries the wielder's body faster), and the weapon's weight is counted once (the 1H formula used to add it to the body too). The CraftingEditor's `thrustMag1H/2H` + `THRUST_REF_SPEED` mirror it.
- `TroopPerks.cs` (not damage math, but shared for the same reason): the troop→perk map read from `ModuleData/rbm_troop_perks.xml`, used by RBMCombat (`CombatModule/TroopPerks/`) and RBMCampaign's party-screen hover.

RBMCombat's `Utilities.GetSkillBasedDamage`/`RBMComputeDamage` are thin forwarders to these, so live combat (which RBMStance's posture crush-through now re-runs through `MissionCombatMechanicsHelper.GetAttackCollisionResults`, see `MeleeBlowPatch.Math.cs` `CalculateHealthDamage`) and auto-resolve (`RBMAutoResolve/Simulation/SimulationWeaponModel.cs`) all use one table. **Retune damage there, never re-copy it into a module** (the AI copy drifted for three years before this). The weapon-type factors (`RBMCombatConfigWeaponType`) were already in RBMConfig.

## Key Conventions

- Harmony patch classes are static inner classes within files named after their domain (e.g., `DamageRework.cs` contains damage-related patches)
- Config values use `"1"`/`"0"` strings for booleans in XML
- Module compatibility checks happen in `OnBeforeInitialModuleScreenSetAsRoot()`
- MissionBehaviors (StanceLogic, StanceVisualLogic, PlayerExhaustionLogic, HitStopLogic under `rbmStanceEnabled`; PlayerArmorStatus, SiegeArcherPoints) are added conditionally in `OnMissionBehaviorInitialize()`
- Localization strings use `{=TAG}Text` format via `TextObject`

## Decompiled game sources

**The full TaleWorlds source is already on disk at `decompiled/<AssemblyName>/`.
Read and grep it directly. Do NOT run `ilspycmd` to decompile a type on demand —
that work is already done, and re-decompiling per-question is pure waste.**

36 assemblies, ~5,400 `.cs` files, one file per type, foldered by namespace —
e.g. `decompiled/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.GameComponents/DefaultPartyWageModel.cs`.
Covers TaleWorlds.\* (CampaignSystem, Core, Engine, MountAndBlade, GauntletUI\*, …),
SandBox\*, StoryMode\*, and NavalDLC\*.

Never guess at a TaleWorlds method body or signature — open the file. Grep for a
type name across `decompiled/` to find it; use the Explore agent for broad sweeps
so the main context stays clean.

The folder is **gitignored** (derived, 42MB, TaleWorlds-owned code), so it exists
on this machine but not for a fresh clone. If it is missing or a lookup turns up an
assembly that isn't there, regenerate with `tools\Decompile-Bannerlord.ps1`
(`-Scope Full` widens beyond the single-player set). See `tools/README.md`.

Two manifests **are** committed, and together they localise a game update:

- `tools/bannerlord-assemblies.lock.json` — SHA256 per source DLL. After an
  update, `.\tools\Decompile-Bannerlord.ps1 -Check` lists which assemblies moved.
- `tools/bannerlord-types.lock.txt` — SHA256 per decompiled type. After
  re-running the script, `git diff` on this file names the individual types that
  changed, i.e. exactly where RBM's Harmony patches may have broken.
