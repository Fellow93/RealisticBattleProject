# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Realistic Battle Mod (RBM) for Mount & Blade II: Bannerlord. A comprehensive combat overhaul mod that rewrites damage calculations, armor mechanics, AI behavior, and adds a stamina/posture system. Built on Harmony 2.4.2 for non-invasive runtime patching of game methods.

Current version: v4.8.1 (`RBMXML/SubModule.xml`). Targets Bannerlord v1.5.4+ (per the
`DependedModules` entries there); currently developed against v1.5.6 (its perk API — `PerkHelper` environment as the
trailing optional argument, `TryGetPerkEffectBonus`, no `BattleEnvironment.None`, no environment overloads of
`GetPerkValue`/`HasPerk` — does not compile against ≤ v1.5.5).

## Build

**Solution:** `RealisticBattle.sln` — .NET Framework 4.7.2, x64 target.

Build with Visual Studio (2017+) or MSBuild:
```
msbuild RealisticBattle.sln /p:Configuration=Release /p:Platform="Any CPU"
```

All 8 projects output DLLs to `../../RBM/bin/Win64_Shipping_Client/` (relative to each project folder, resolving to the `RBM/bin/` directory within the Bannerlord Modules tree).

Single-project build (from memory — MSBuild path is under VS `18\Community`, and `Platform` must be quoted with its space):
```
"C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe" RealisticBattle.sln /p:Configuration=Debug "/p:Platform=Any CPU" /t:RBM /verbosity:minimal
```

**Debug launch:** Bannerlord.exe with `/singleplayer _MODULES_*Native*SandBoxCore*SandBox*StoryMode*CustomBattle*RBM*_MODULES_`

Testing is mostly manual, in game. The one exception is `RBMCampaign.Tests/` (NUnit, net472, not in the sln; build/run commands in its README). It holds executable specs for RBMCampaign's game-free formulas: market price curve, spoils carried on upgrade, wage table. When you change one of those formulas, run it. To add a spec for a campaign rule, first move the rule's math into a pure function that takes plain values.

## Architecture

### Module Structure (8 C# projects)

**RBM** — Main coordinator. Entry point: `RBM.SubModule` (extends `MBSubModuleBase`). Manages Harmony instance lifecycle, conditionally patches/unpatches each subsystem based on config toggles. References RBMAI, RBMCombat, RBMStance, RBMTournament, RBMCampaign and RBMAutoResolve.

**RBMAI** — Battle AI (the posture/stamina system, AI kick/bash and the combat slow motion moved out to RBMStance on 2026-10-13). Patcher entry: `RBMAiPatcher` (uses `Harmony.PatchAll()`, so file location is cosmetic — patches are discovered by attribute, not registered by hand). References RBMConfig and RBMStance (Frontline reads posture/stamina, the developer battle-stats overlay `AiModule/Diagnostics/BattleStatsLogic.cs` shows the kick/bash counters). As of 2026-07-18 the module was reorganized from a handful of multi-thousand-line monoliths into subsystem folders under `AiModule/`. Large classes were split across files using `partial class` (and, for `Utilities`, partial static files at project root) so no call sites changed. Namespace stays flat `RBMAI`; the old-style csproj lists every file with an explicit `<Compile Include>` — **update it when adding/moving files**. Layout:
- `AiModule/Behaviors/` — formation behavior patches (`SkirmishBehaviors`, `DefenseBehaviors`, `FlankBehaviors`, `AdvanceBehavior`, `AgentSpeedAndParams`, `MiscBehaviorPatches`); custom `RBMBehavior*` subclasses under `Behaviors/Custom/`.

Men go BACK to the garrison (XP pro rata, purses via `TransferSpoils`, wounded too) when vanilla's `RemoveSettlementParties` stands a patrol down (keep-gate, or a peaceful owner change — `OnSettlementOwnerChangedEvent` prefix/finalizer marks the detail; `BySiege`/`ByRebellion` keep vanilla's destroy), and as surplus over the current size when it rests at home (`TrimSurplus`: unmatched men, then lowest tier; daily + on entering home); never while the patrol or fief is in a MapEvent/siege. Land patrols get +0.5 base map speed (`SpeedBonus`, a `DefaultPartySpeedCalculatingModel.CalculateBaseSpeed` postfix) and, without a town Guard House (castles always), vanilla's level-0 patrol security +0.5/day (`DefaultSettlementSecurityModel.CalculateSecurityChange` postfix). ⚠️ The speed model reads `PartySizeLimit` inside the parallel movement tick: the plain size query only reads `_partyLimit` (ConcurrentDictionary, written on the main thread by `RefreshLimit` at session launch / daily / spawn / refill / stall / trim; an off-thread miss returns max(6, head count) and writes nothing); only the tooltip (`includeDescriptions`) computes. The main module's always-on `RBM/PatrolReplenishGuard.cs` (`com.rbmmain`, Priority.Last, reads `__runOriginal`) skips vanilla's `ReplenishParty` when the template is null, so a castle / no-Guard-House patrol left on the map with the feature off cannot NRE (nothing can guard a save once RBM is removed). Only the averaged pot is saved (`RBM_patrolAveragePot`, `PatrolUpkeep.SyncData` from the settlement-wealth behaviour); the rest is session state.
- `Production/` — village production, villager convoys/deliveries, town food supply and storage, citizen and workshop demand.
- `Economy/` — market prices and liquidity, caravan capital, recruit supply, trade-good values.
- `Power/` — `StrategicTroopPower` (equipment-based party strength, priced through RBMAutoResolve's kit model; its `Enabled` also needs `rbmCombatEnabled` — with RBM Combat off the game's own strength is used, there is no combat-off pricing path, and `ArmyStrengthFloorPatch`'s 700 falls back to vanilla's 1000) and the strategic-AI gates (`SiegeDecisionGate` etc.). `Spectate/` — no-agent AI-vs-AI spectator battle.

Excluded from `MercenaryContractPay`. ⚠️ Every patch must stay a no-op for clans that are not companies (`MercenaryCompanies.IsCompany`).

### Harmony Patching Pattern

All game modifications use Harmony `[HarmonyPatch]` attributes on static inner classes with `Prefix`, `Postfix`, or `Finalizer` methods. Patches target `TaleWorlds.MountAndBlade` types via reflection. Each module has a dedicated `Harmony` instance (`com.rbmai`, `com.rbmcombat`, `com.rbmstance`, `com.rbmt`, `com.rbmmain`, `com.rbmcampaign`, `com.rbmautoresolve`) enabling selective enable/disable.

The patching lifecycle flows: `SubModule.OnSubModuleLoad()` → loads config → `RegisterSubModuleTypes()` / `OnGameStart()` → `ApplyHarmonyPatches()` which conditionally patches each module.

### Configuration

**Changing a saved setting for every player in a release:** add one entry to `ForcedSettings` in `RBMConfig/Config/RBMConfig.Core.cs` (new unique id, XPath, value) and give the code default the same value. It is written once onto each saved config on the first start of that release (ids recorded under `/Config/AppliedForcedSettings`; fresh configs only mark them), and the player's later choice sticks. Never edit or remove a shipped entry. Only for absolute values: a change relative to the player's own value (like the sling stone rescale) still needs a hand-written marker migration. Never bump `CONFIG_VERSION` for this, it resets the whole config.

Settings are static fields on `RBMConfig.RBMConfig`, persisted to user XML at `Utilities.GetConfigFilePath()`. Key toggles: `rbmAiEnabled`, `rbmCombatEnabled`, `rbmStanceEnabled` (RBMStance's module switch, independent of `rbmAiEnabled`; `postureEnabled`, `staminaEnabled`, `postureGUIEnabled`, `playerPostureMultiplier`, `aiKickBashEnabled` and `hitStopEnabled` are its sub-options), `rbmTournamentEnabled`, `rbmCampaignEnabled`, `simulationEquipmentEnabled` (RBMAutoResolve's module switch, independent of `rbmCampaignEnabled`). Each toggle gates whether the corresponding Harmony patches are applied. RBMCampaign also reads tuning multipliers (e.g. `troopUpgradeCostMultiplier`, where `0` disables the spoils system entirely) — see `RBMConfigViewModel` for the full set.

### XML Data Files

`RBMXML/` contains 30+ XML files loaded by Bannerlord's XML system (registered in `SubModule.xml`). These modify items (weapons, armor, horses), crafting pieces, siege engines, NPC characters, and weapon descriptions. `XmlLoadingPatches.cs` handles XML merging/preprocessing.

`RBM_WS_XML/` contains compatibility files for the War Sails (Naval) DLC.

Troop skills/levels/equipment rosters in `RBMCombat_unit_overhaul.xml` (+ the WS one) can be edited with the local page in `tools/TroopLoadoutEditor/` (run its `Build-TroopLoadoutData.ps1` first; its README explains how `XmlLoadingPatches` applies those files). Upgrade targets are edited with `tools/TroopUpgradeTreeEditor/` (tree diagrams + checks), which has no data or build script of its own: it loads the loadout editor's data and `troop-loadout-core.js`, so both pages export the same files through one splice path (re-run the script after exporting from either). Its README lists the verified game rules (later definition replaces `UpgradeTargets`, cycles crash, no count limit, tier ≤ → 0 XP). Items in RBM's item files are edited with `tools/ItemEditor/` (run its `Build-ItemData.ps1` first; it also loads `troop-loadout-core.js`): the export patches only changed attributes in every RBM file defining the id (both ranged twins), and its README covers RBM's full-replacement item rule and the tier/price formulas. Crafting pieces and templates are edited with `tools/CraftingEditor/` (run its `Build-CraftingData.ps1` first): RBM's crafting files are appended, not merged, so an id is deserialized again after vanilla's (start-tag attributes reset, child elements only when present, usable pieces accumulate); the page replays that and recomputes every crafted item's stats with the game's crafting math plus RBM's patches (README: formulas and approximations).

### Large Utility Files

RBMAI, RBMCombat and RBMConfig each have their own `Utilities` (partial static files in RBMAI/RBMCombat, see above) with helpers for combat math, physics and config management; RBMStance has `StanceUtilities`.

**Shared damage math lives in `RBMConfig/Shared/`** (2026-09-26), because RBMStance (the posture system, formerly in RBMAI) does not reference RBMCombat (RBMCombat references it) and RBMConfig is the one module both reference:
- `SkillDamage.cs`: `GetSkillBasedDamage` (the per-weapon-class skill coefficient/clamp table) and the punch magnitude helpers (`GetPunchMaterialFactor`/`GetPunchMagnitude`). `MeleeSkillDR`/`MeleeSkillMod` (2026-10-14) are the melee-only skill curve (c = 200, scaled to equal the shared 600 curve and clamp(skill/250) at skill 100), used by melee swing/thrust speed, thrust energy, `GetSkillBasedDamage` for melee blows, the melee attack/handling animation speeds (`CalculateVisualSpeeds`, live in `RangedRework.OverrideWeaponEquipped` + tooltip), the weapon tooltips' damage and the auto-resolve (+ CraftingEditor mirror); missiles and kicks/bashes keep `MissileBallistics.EffectiveSkillWithDR`.
- `BlowDamage.cs`: `RBMComputeDamage` (armor, penetration and blunt trauma). Trauma (2026-10-14): every damage type's trauma (the stopped part × carry × armour reduction) is × `GetTraumaMaterialFactor` (mail 1.2, plate 0.8, else 1; from the `armorMaterial` argument, so callers that pass `None` — tooltips, shield damage — get 1). Blunt carry = `BluntTraumaBase` 0.6 × per-class `ExtraBluntFactorBlunt`, × `UnarmedBluntTraumaFactor` 0.75 for `"unarmedAttack"` (kicks/bashes/punches; charges and falls are `"otherDamage"`); cut/pierce carries are the per-class `ExtraBluntFactorCut/Pierce`. The penetration threshold has no material factor on purpose (armor values are set by a bodkin; cuts never get through mail/plate). The per-class rules are two lookups, not a switch: `GetThrustBonus(weaponType)` (×One/TwoHandedThrustDamageBonus on Pierce for the thrust-scaled classes, 1 otherwise; the auto-resolve divides by it because its thrust magnitudes are already unscaled) and the factor row (only the listed classes read the config; any other string, e.g. `"unarmedAttack"`, gets the base rule). Weapon-class aliases (LowGripPolearm → OneHandedPolearm, Pick → Mace) live in `WeaponTypeKeys.NormalizeWeaponType`, used by both `BlowDamage` and `SkillDamage`. The shared math has no UI side effects: the armor penetration message is shown by its caller in `DamageRework.Core.cs`. Per-class blunt factors are relative to the base, so changing the base needs a saved-config rescale for any class meant to keep its trauma (sling stones: `SlingStoneBluntBaseRescaled` in `RBMConfig.Core.cs`).
- `ThrustEnergy.cs` (2026-10-12): melee thrust speed (`CalculateThrustSpeed`) and thrust energy (`OneHanded`/`TwoHanded`, raw, before `ThrustMagnitudeModifier`), used by the live blow + tooltip (RBMCombat `Utilities.Physics.cs` forwarders) and the auto-resolve (`SimulationWeaponModel.GetThrustEnergy`). The body term runs at no more than the class's median thrust speed (`GetReferenceThrustSpeed`, so a light shaft no longer carries the wielder's body faster), and the weapon's weight is counted once (the 1H formula used to add it to the body too). The CraftingEditor's `thrustMag1H/2H` + `THRUST_REF_SPEED` mirror it.
- `TroopPerks.cs` (not damage math, but shared for the same reason): the troop→perk map read from `ModuleData/rbm_troop_perks.xml`, used by RBMCombat (`CombatModule/TroopPerks/`) and RBMCampaign's party-screen hover.

RBMCombat's `Utilities.GetSkillBasedDamage`/`RBMComputeDamage` are thin forwarders to these, so live combat (which RBMStance's posture crush-through now re-runs through `MissionCombatMechanicsHelper.GetAttackCollisionResults`, see `MeleeBlowPatch.Math.cs` `CalculateHealthDamage`) and auto-resolve (`RBMAutoResolve/Simulation/SimulationWeaponModel.cs`) all use one table. **Retune damage there, never re-copy it into a module** (the AI copy drifted for three years before this). The weapon-type factors (`RBMCombatConfigWeaponType`) were already in RBMConfig.

## Key Conventions

- Harmony patch classes are static inner classes within files named after their domain (e.g., `DamageRework.cs` contains damage-related patches)
- Config values use `"1"`/`"0"` strings for booleans in XML
- Module compatibility checks happen in `OnBeforeInitialModuleScreenSetAsRoot()`
- MissionBehaviors (StanceLogic, StanceVisualLogic, PlayerExhaustionLogic, HitStopLogic under `rbmStanceEnabled`; PlayerArmorStatus, SiegeArcherPoints) are added conditionally in `OnMissionBehaviorInitialize()`
- Localization strings use `{=TAG}Text` format via `TextObject`

## Decompiled game sources

**The full TaleWorlds source is already on disk at `decompiled/<AssemblyName>/`.
Read and grep it directly. Do NOT run `ilspycmd` to decompile a type on demand —
that work is already done, and re-decompiling per-question is pure waste.**

36 assemblies, ~5,400 `.cs` files, one file per type, foldered by namespace —
e.g. `decompiled/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem.GameComponents/DefaultPartyWageModel.cs`.
Covers TaleWorlds.\* (CampaignSystem, Core, Engine, MountAndBlade, GauntletUI\*, …),
SandBox\*, StoryMode\*, and NavalDLC\*.

Never guess at a TaleWorlds method body or signature — open the file. Grep for a
type name across `decompiled/` to find it; use the Explore agent for broad sweeps
so the main context stays clean.

The folder is **gitignored** (derived, 42MB, TaleWorlds-owned code), so it exists
on this machine but not for a fresh clone. If it is missing or a lookup turns up an
assembly that isn't there, regenerate with `tools\Decompile-Bannerlord.ps1`
(`-Scope Full` widens beyond the single-player set). See `tools/README.md`.

Two manifests **are** committed, and together they localise a game update:

- `tools/bannerlord-assemblies.lock.json` — SHA256 per source DLL. After an
  update, `.\tools\Decompile-Bannerlord.ps1 -Check` lists which assemblies moved.
- `tools/bannerlord-types.lock.txt` — SHA256 per decompiled type. After
  re-running the script, `git diff` on this file names the individual types that
  changed, i.e. exactly where RBM's Harmony patches may have broken.
