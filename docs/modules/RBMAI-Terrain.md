# RBMAI — orders (ChargeGuard), formations, diagnostics, BattleTerrain API and terrain overlays

Moved verbatim from CLAUDE.md on 2026-10-30. Keep adding design notes for this area here, not in CLAUDE.md.

- `AiModule/Orders/` — movement-order patches. `AiModule/UI/` — formation-marker patches. `AiModule/Siege/` (+ `SiegeArcherPoints/`), `AiModule/Spawning/`, `AiModule/Misc/`. `AiModule/Diagnostics/` — AI behavior log + the developer battle-stats overlay (`BattleStatsLogic`, dev mode; its tactics panel, refreshed once a second on the main thread, lists each team AI's options ranked by final weight via `TacticWeightProbe.Evaluate`, with army fit = final ÷ (`TacticSelection.TryGetMultiplier` × `TerrainFactorFor`), the current tactic marked, and a terrain on/not-read/applied line; row VMs in `BattleStatsTacticsVM.cs` are reused; each team block also shows its `TerrainFlankPlan` line (own left/right covered or open + reason, attack side + route time) and a band above the blocks the `BattleTerrain.Current` map summary (mid corridor ÷ wider frontage) and feature counts). Developer Mode also adds `AiModule/Terrain/TerrainFeatureOverlay.cs` (prefab `RBMXML/GUI/Prefabs/RBMTerrainFeatures.xml`, MissionLogic next to `BattleStatsLogic`), inert until Ctrl+Shift+D (was T; vanilla's Ctrl+D debug hotkeys also accept Shift, plain D strafes): it labels every feature-map entry (hills, crests, chokes, open fields, flank ends coloured covered/open by the published flank plan, woods/rough, water, fords, each army's centre with its attack side, archer spots with a dotted line from each formation holding one) on the battlefield and outlines the areas with dots (`BattleTerrain.Outlines`, traced on the worker by `BattleTerrainRead.Outlines.cs` only in developer mode: flood fill + cell-edge boundary thinned to ~5 m, choke gap lines, spot room circles, ≤ 4,000 dots; log OUTLINES; plus, with their own 600-dot budget, each side's `TerrainCavalry` charge lanes and a dotted line + label from each formation riding to one; the legend shows dots on screen and ms/frame), reading only the immutable snapshot (heights from its grid + 2 m) and pooling the widgets once per snapshot, so the per-frame work is the `WorldToScreen` projection alone. Ctrl+Shift+D CYCLES off → terrain → terrain + decisions → decisions only → off; the decision layer (`TerrainFeatureOverlay.Decisions.cs`, own pools ≤ 40 labels / 600 dots, texts every 0.5 s) labels each formation with its tactic role (the current tactic's reflected `Formation` fields), active behavior + best two others scored as `FindBestBehavior` does (`GetAIWeight × WeightFactor`, keep bonus noted, no `PrecalculateMovementOrder`), claim, order kind and a dotted line to the CACHED `Formation.OrderPosition` (never a computed order position or spatial query), and each AI team with its tactic ranking from the shared `TacticWeightProbe.Rank` (also the battle stats panel's). **Battlefield terrain API: `BattleTerrain.Current`** (`AiModule/Terrain/BattleTerrain.cs`) — the typed, immutable terrain snapshot of the current land field battle, read by the tactic choice through `TerrainTacticFactors` (computed from it once at the publish; no other consumer yet). Computed in EVERY field battle with RBM AI on by `AiModule/Terrain/BattleTerrainLogic.cs` (MissionLogic added in `RBM/SubModule.cs` under `rbmAiEnabled` alone; field battles only): `BattleTerrainRead.Build` grids the whole playable map in its AfterStart (mission load); on the first tick after deployment (or once the AI has ticked 3 s without a deployment phase) `BattleTerrainRead.Gather` (MAIN thread, `BattleTerrainRead.Gather.cs` — the ONLY file of the read that calls the engine: Build, the men, the obstacle rays, forest regions) copies everything into an immutable `Inputs` bundle, `BattleTerrainRead.Compute` runs on a background `Task.Run` over the grid + bundle only (A* paths, widths, flood fill, sight lines; no Mission/Agent/Scene/MBRandom/engine call — keep it that way), and the logic polls the task each tick and publishes the snapshot (volatile field, MAIN thread) a few frames after deployment, keeping it, grid included, for the whole mission; a result finishing after the mission ended is dropped (generation token); cleared at mission end and in `MissionStartReset`. Timing in the snapshot/log: `MainMs` (the one-frame cost), `BackgroundMs`, `WallMs`, `ComputedAt` (gather) / `PublishedAt`. It holds base/Space/Open/Mounted/Sight groups (each with `Ms` + `Error`) — CUT 2026-10-24 (user: remove complexity, no gameplay change) to what decision code reads: per-side `Attacker`/`Defender` (centroid, snap, frontage, force, speeds, flank routes, run-up onto the enemy, fields of fire `FireAny`, `ClearLine`, `ExitFront`), the width profile (`Space.WidthProfile`, read by the route chokes), `SameGround`, field clutter/steep/deep shares, `HeightDifference`, `FieldWidth`, the widest corridor A→D (`Corridor*`/`MidCorridor*`: exact maximin route by union-find in descending clearance, bottleneck width ÷ frontage), the open-field labels; the Height / Conditions / MapType groups, the type hint, the open-land totals, the open route, the control rays and ray tallies, orbit room and the hill/crest/choke diagnostic extras are GONE (they were log-only); and grid helpers (`IsWalkable`/`HeightAt`/`SampleHeight`/`SlopeAt`/`IsWet`). Feature map (2026-10-21): `BattleTerrain.Features` — the map as a short list of named places, built on the worker as the last group (`BattleTerrainRead.Features.cs`, no engine call; the obstacle rays carry their target cell so woods are classified without new casts), typed immutable classes in `BattleTerrain.Features.cs` (kinds Hill/Crest/Choke/OpenField/Flank/Woods/Rough/Water/Ford; each with `Id` "hill1", `Position`, `Area`/`Length`/`Width` on the axis, per-army `Attacker`/`Defender` distance + own-frame bearing, `Between`, `Side`, `Importance`, plus typed kind fields; capped per kind, most important first, never null; CHOKES (2026-10-22, user: bridges/fords were missed — the old ones were only route bottlenecks < 1.5 × frontage; "choke should also be between deepwater"): `BattleTerrainRead.Chokes.cs`, the LAST feature step: a map-wide passage scan = clearance-map saddles by union-find in descending clearance (merge = two areas meet, loop = round an obstacle), 2r ≤ min(80 m, 1.5 × wider frontage), both sides open into a room, one per passage, no short way round with the passage cut (grid A*; a 2× cut retry for an obstacle inside it); plus the old route bottlenecks (merged within 40 m). ChokeFeature: Type bridge|ford|pass|neck|mixed, BoundedBy, Width/Length, LineStart/LineEnd/LineDirection/PassageDirection, MouthA/B, AttackerSide/DefenderSide + Sides same|opposite (side flood from both mouths, cut closed, top 8 only), Separates, OnRoute, WetShare, WaterId/FordId; log: the FEATURE choke fields; bridge saddles (≤ 2 cells from a bridge cell) are checked first (the 10 ms budget dropped 45/90 candidates), Type bridge = bridge cells on the stretch or within r + 1 step of it (never ford; Position moved onto the deck, BoundedBy read there); crossings (Sides opposite) skip ChokeHold's At filter too. `Grid.Bridge`/deep (Build, AfterStart, 2026-10-22 fix): taken from `DeepWaterNavBlocker.Grid` (`DeepWaterGrid.Bridge`/`BridgeCount`/`FindBridgeCells`, its EarlyStart ProbeBridge cells — the blocker's own behaviour unchanged) when it exists: deep = its cell under the centre, bridge = any of its bridge cells in the 4 m square whose deck (`DeckWalkable`: GetHeightAtPoint excl. AgentOnly walls, ≥ 0.5 m above the bed, navmesh face at the deck with checkIfDisabled false, face centre above the bed) carries the navmesh; a wet cell with no bed navmesh but a navmeshed deck = walkable, a bridge cell only when joined to a deep deck (`DeckShallowBridge`); no blocker grid → the old per-cell ProbeCell. ROOT CAUSE: Build's own ProbeCell runs AFTER the blocker's face pass (EarlyStart < AfterStart); battle_terrain_biome_088 had GRID bridgeExcluded=72 but 0 bridge cells in the choke scan (the deck read as deep water). TERRAIN_WATER (src, deep/bridge m² grid vs blocker vs own probe, deepDisagree, deckMissing, deckFacesOff = deck faces the blocker switched off, deckShallow) is the sanity line — UNVERIFIED in game — a failed step leaves its kind empty and says so in `FeatureMap.Error`); future tactic/behavior code should query it (`Hills`/`Chokes`/... or `Of(kind)`, `FeatureById`) instead of re-deriving from the grid; logged as FEATURES + one FEATURE line each. Woods (2026-10-21): trees in these scenes are entity-less static bodies NOT flagged as flora (rays come back noEnt) and punch only small navmesh holes, so the woods mask (`BattleTerrain.WoodsMap`, `IsWoods`) = map Forest `TacticalRegion`s (radius gathered; DifficultTerrain ones → Rough "difficult") + small-obstacle density (no-navmesh components ≤ 64 m², ≥ `WoodsDensity` 0.05 of a ~24 m window, a fixed first guess), rays only as confirmation (large clusters mostly inside join, entity-dominated density areas are vetoed); it is cavalry bad ground, no archer spot stands in it and ≥ 12 m of it blocks a spot's sight line. ⚠️ THREADING: AI-thread readers copy the reference to a local, null-check it and only read; never call the engine for terrain off the main thread (Build/Gather do). ⚠️ The team AI's first tactic decision comes BEFORE deployment ends (t=0.13 in a log) and the publish lands a few frames AFTER it ends, so every consumer must handle `Current == null` early in the battle (and outside field battles, when a side had no men, or when the background part faulted). Its log is optional and its own: `logs/terrain/`, one file per field battle (`BufferedLogWriter` + `LogRetention`, like the deep-water log), toggle `battleTerrainLoggingEnabled` (Debug & Logging, XML `/Config/RBMAI/BattleTerrainLoggingEnabled`, default off), lines formatted from the snapshot by `BattleTerrainLogFormat.cs` (TERRAIN + TERRAIN_*, field docs in `docs/terrain-log-format.md` — the log header only points there; it used to be part of the AI behavior log), plus the terrain tactic lines PREDICT / TACTIC / TACTICSUMMARY (see `TerrainTacticFactors` above). What the read measures (`Build` grids the whole playable map — boundary bounding box, ≤ 80k cells, ≥ 4 m; `Compute` only reads the grid and the gathered bundle): height difference between the armies' centres, frontages, field clutter = no-navmesh share, deep water via the blocker's grid (else `DeepWaterNavBlocker.ProbeCell`), slope. Not saved to disk (user 2026-10-20). `partial static class` split (`.Gather.cs` = main thread/engine; `.Space`/`.Open`/`.Mounted`/`.Sight.cs` = background, one group / log line each after TERRAIN, Open after Space: `TERRAIN_SPACE` `widths=` profile/flank routes, `TERRAIN_OPEN` corridor/exit/clear line, `TERRAIN_MOUNTED` charge run-up, `TERRAIN_SIGHT` terrain fields of fire/obstacle rays); the grid also holds wet cells, slopes, a summed-area table of heights and the clearance map (`Grid.Clearance`: each walkable cell's centre-to-centre distance to the nearest NoNav/Deep/Out cell, the ring beyond the grid counting as Out; exact Felzenszwalb–Huttenlocher distance transform in `Build`, O(cells), timed as `clearMs`) and the edge distance (`Grid.EdgeDistance`, the same transform with Out cells alone, `edgeMs`; `BattleTerrain.EdgeDistanceAt`/`NearEdge`): places within `BattleTerrainRead.EdgeMargin` (60 m, first guess) of the map edge are never used — dropped from the feature map (water and flanks kept, open fields trimmed before labelling), archer spots and cavalry reform/orbit/lane starts, flank routes keep 30 m off it, counts on FEATURES/SPOTS/CAVALRY; and the main file the shared A* / straight walker / flood fill. Obstacle rays (≤ 160 through no-navmesh cells bordering walkable ground, 1.2 m, `CommonCollisionExcludeFlags`): flora and terrain bodies carry no `GameEntity` (that is why the first logs showed rayEntity=0), so a hit with no entity is re-cast with `BodyOwnerFlora`, then `BodyOwnerTerrain` added to the exclude mask (native `OrderFlag`/`OrderTroopPlacer` exclude flora that way) to tell flora / terrain / other apart — the owner masks are UNVERIFIED in game. The log is ASCII only (bearings `44deg`).
