# RBMConfig — config store, settings UI, shared damage math

Moved verbatim from CLAUDE.md on 2026-10-30. Keep adding design notes for this area here, not in CLAUDE.md.

**RBMConfig** — Configuration system with no project dependencies. Static fields in `RBMConfig.RBMConfig` loaded from user XML config. Includes Gauntlet-based in-game settings UI (`RBMConfigScreen`/`RBMConfigViewModel`). As of 2026-07-19 the two monoliths were split by config category via `partial class` (flat namespace `RBMConfig`; explicit `<Compile Include>` csproj — **update it on add/move**): the store `partial static class RBMConfig` lives in `Config/` (`.Core.cs` holds the module toggles + all XML `LoadConfig`/`parseXmlConfig`/`saveXmlConfig` methods, which reference fields across the sibling `.Combat.cs`/`.Campaign.cs`/`.Simulation.cs`); the settings ViewModel is split the same way under `RBMConfigUI/` (`RBMConfigViewModel.Core.cs` keeps the ctor + `ExecuteDone`/`ExecuteResetToDefault`/`ExecuteCancel` + `Hint`/`RefreshValues`, the `.Combat`/`.Campaign`/`.Simulation.cs` files hold only the `[DataSourceProperty]` declarations). Completeness is compiler-enforced — the retained Core methods reference every field/property, so a dropped or duplicated declaration fails the build. `Shared/` holds the damage math used by RBMCombat, RBMStance, RBMAI, RBMCampaign and RBMAutoResolve (see "Large Utility Files" below), and `Shared/Logging/` (namespace `RBMConfig.Logging`) the log-file primitives RBMCampaign's logs and RBMAutoResolve's `SimulationLog` share: `BufferedLogWriter`, `LogRetention`, `CampaignLogClock` (the campaign-clock readiness check, formerly `SpoilsLog.CampaignClockReady`).

### Configuration

**Changing a saved setting for every player in a release:** add one entry to `ForcedSettings` in `RBMConfig/Config/RBMConfig.Core.cs` (new unique id, XPath, value) and give the code default the same value. It is written once onto each saved config on the first start of that release (ids recorded under `/Config/AppliedForcedSettings`; fresh configs only mark them), and the player's later choice sticks. Never edit or remove a shipped entry. Only for absolute values: a change relative to the player's own value (like the sling stone rescale) still needs a hand-written marker migration. Never bump `CONFIG_VERSION` for this, it resets the whole config.

Settings are static fields on `RBMConfig.RBMConfig`, persisted to user XML at `Utilities.GetConfigFilePath()`. Key toggles: `rbmAiEnabled`, `rbmCombatEnabled`, `rbmStanceEnabled` (RBMStance's module switch, independent of `rbmAiEnabled`; `postureEnabled`, `staminaEnabled`, `postureGUIEnabled`, `playerPostureMultiplier`, `aiKickBashEnabled` and `hitStopEnabled` are its sub-options), `rbmTournamentEnabled`, `rbmCampaignEnabled`, `simulationEquipmentEnabled` (RBMAutoResolve's module switch, independent of `rbmCampaignEnabled`). Each toggle gates whether the corresponding Harmony patches are applied. RBMCampaign also reads tuning multipliers (e.g. `troopUpgradeCostMultiplier`, where `0` disables the spoils system entirely) — see `RBMConfigViewModel` for the full set.

### Large Utility Files

RBMAI, RBMCombat and RBMConfig each have their own `Utilities` (partial static files in RBMAI/RBMCombat, see above) with helpers for combat math, physics and config management; RBMStance has `StanceUtilities`.

**Shared damage math lives in `RBMConfig/Shared/`** (2026-09-26), because RBMStance (the posture system, formerly in RBMAI) does not reference RBMCombat (RBMCombat references it) and RBMConfig is the one module both reference:
- `SkillDamage.cs`: `GetSkillBasedDamage` (the per-weapon-class skill coefficient/clamp table) and the punch magnitude helpers (`GetPunchMaterialFactor`/`GetPunchMagnitude`). `MeleeSkillDR`/`MeleeSkillMod` (2026-10-14) are the melee-only skill curve (c = 200, scaled to equal the shared 600 curve and clamp(skill/250) at skill 100), used by melee swing/thrust speed, thrust energy, `GetSkillBasedDamage` for melee blows, the melee attack/handling animation speeds (`CalculateVisualSpeeds`, live in `RangedRework.OverrideWeaponEquipped` + tooltip), the weapon tooltips' damage and the auto-resolve (+ CraftingEditor mirror); missiles and kicks/bashes keep `MissileBallistics.EffectiveSkillWithDR`.
- `BlowDamage.cs`: `RBMComputeDamage` (armor, penetration and blunt trauma). Trauma (2026-10-14): every damage type's trauma (the stopped part × carry × armour reduction) is × `GetTraumaMaterialFactor` (mail 1.2, plate 0.8, else 1; from the `armorMaterial` argument, so callers that pass `None` — tooltips, shield damage — get 1). Blunt carry = `BluntTraumaBase` 0.6 × per-class `ExtraBluntFactorBlunt`, × `UnarmedBluntTraumaFactor` 0.75 for `"unarmedAttack"` (kicks/bashes/punches; charges and falls are `"otherDamage"`); cut/pierce carries are the per-class `ExtraBluntFactorCut/Pierce`. The penetration threshold has no material factor on purpose (armor values are set by a bodkin; cuts never get through mail/plate). The per-class rules are two lookups, not a switch: `GetThrustBonus(weaponType)` (×One/TwoHandedThrustDamageBonus on Pierce for the thrust-scaled classes, 1 otherwise; the auto-resolve divides by it because its thrust magnitudes are already unscaled) and the factor row (only the listed classes read the config; any other string, e.g. `"unarmedAttack"`, gets the base rule). Weapon-class aliases (LowGripPolearm → OneHandedPolearm, Pick → Mace) live in `WeaponTypeKeys.NormalizeWeaponType`, used by both `BlowDamage` and `SkillDamage`. The shared math has no UI side effects: the armor penetration message is shown by its caller in `DamageRework.Core.cs`. Per-class blunt factors are relative to the base, so changing the base needs a saved-config rescale for any class meant to keep its trauma (sling stones: `SlingStoneBluntBaseRescaled` in `RBMConfig.Core.cs`).
- `ThrustEnergy.cs` (2026-10-12): melee thrust speed (`CalculateThrustSpeed`) and thrust energy (`OneHanded`/`TwoHanded`, raw, before `ThrustMagnitudeModifier`), used by the live blow + tooltip (RBMCombat `Utilities.Physics.cs` forwarders) and the auto-resolve (`SimulationWeaponModel.GetThrustEnergy`). The body term runs at no more than the class's median thrust speed (`GetReferenceThrustSpeed`, so a light shaft no longer carries the wielder's body faster), and the weapon's weight is counted once (the 1H formula used to add it to the body too). The CraftingEditor's `thrustMag1H/2H` + `THRUST_REF_SPEED` mirror it.
- `TroopPerks.cs` (not damage math, but shared for the same reason): the troop→perk map read from `ModuleData/rbm_troop_perks.xml`, used by RBMCombat (`CombatModule/TroopPerks/`) and RBMCampaign's party-screen hover.

RBMCombat's `Utilities.GetSkillBasedDamage`/`RBMComputeDamage` are thin forwarders to these, so live combat (which RBMStance's posture crush-through now re-runs through `MissionCombatMechanicsHelper.GetAttackCollisionResults`, see `MeleeBlowPatch.Math.cs` `CalculateHealthDamage`) and auto-resolve (`RBMAutoResolve/Simulation/SimulationWeaponModel.cs`) all use one table. **Retune damage there, never re-copy it into a module** (the AI copy drifted for three years before this). The weapon-type factors (`RBMCombatConfigWeaponType`) were already in RBMConfig.
